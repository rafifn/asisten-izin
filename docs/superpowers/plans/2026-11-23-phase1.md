# Asisten Izin Kuliner Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A local app where a food/beverage micro or small business owner
describes their business in Indonesian and gets KBLI 2025 codes, risk levels and
an ordered, sourced permit checklist.

**Architecture:** Next.js renders the UI and calls a FastAPI backend, which owns
a fixed pipeline: redact → understand (Claude) → hybrid KBLI search
(Postgres + pgvector) → select from candidates (Claude) → deterministic permit
lookup → log. Rules data lives in YAML files under `data/` and is loaded into
Postgres as numbered data releases.

**Tech Stack:**
- Python 3.12 (`uv`), FastAPI, Pydantic v2, psycopg 3 + `pgvector`, `anthropic`
  SDK, `sentence-transformers` (`BAAI/bge-m3`), pytest, ruff, mypy
- Node 22, pnpm, Next.js 16, React 19, Tailwind 4, shadcn/ui, Vitest + Testing
  Library, Playwright
- Postgres 17 + pgvector (Docker image `pgvector/pgvector:pg17`)

**Spec:** `docs/design.md`

## Global Constraints

- KBLI version is `2025` (Peraturan BPS 7/2025). Permits follow PP 28/2025.
  Never use KBLI 2020 or PP 5/2021 as a data source, except the 2020→2025
  conversion table.
- The LLM never produces permits, risk levels, or KBLI codes outside the
  candidate list. Permit text comes only from data rows.
- Every `permit` and every `permit_rule` must have `source_regulation`,
  `source_url` and `last_verified`, or the loader refuses the data.
- Rows are never deleted. Rows that are no longer valid get `valid_to`.
- Model: `claude-opus-5-5`, called only through the official `anthropic` Python
  SDK.
  - Use structured outputs for every call.
  - Set effort explicitly on every call.
  - Turn on server-side refusal fallbacks: beta `server-side-fallback-2026-07-01`
    with `fallbacks="default"`.
  - Pricing for cost logging: $4.00 per 1M input tokens, $20.00 per 1M output
    tokens.
- Embeddings: `BAAI/bge-m3`, dimension 1024, computed when data is loaded.
- At most 2 clarifying questions, in at most 1 round. A request that carries
  `answers` never gets questions back.
- Retrieval returns at most 20 candidates per activity, merged with reciprocal
  rank fusion with k = 60.
- Selection picks 1 primary code and at most 2 alternatives per activity.
- The stale warning shows when any `last_verified` used in the answer is older
  than 183 days.
- Input `description` is 3 to 2000 characters after trimming.
- All error responses use `{"error": {"code": "...", "message": "..."}}`. Codes:
  `invalid_input` (400), `not_found` (404), `llm_unavailable` (503),
  `internal` (500).
- All user-facing copy is in Indonesian. The disclaimer text is exactly:
  `Bukan nasihat hukum. Cek ulang di oss.go.id`.
- Local ports: Postgres `127.0.0.1:5433` (5432 is used by the owner's shoplink
  project), API `8000`, web `3000`.
- Secrets: read `ANTHROPIC_API_KEY` from `.env`, or use an `ant auth login`
  profile. Never commit `.env`.

## Review Focus

1. **The Claude API is down, times out or rate-limits.** The user gets HTTP 503
   `llm_unavailable` with a friendly message, never a 500 or a stack trace. The
   UI shows "Coba lagi sebentar lagi". *(Task 9: `test_llm_failure_returns_503`;
   Task 10: `shows retry message on 503`.)*
2. **Very short or vague input** such as "kopi" or "jualan makanan" leads to
   clarifying questions, not out-of-scope. *(Task 11: eval cases `vague-01`..`vague-03`.)*
3. **Clarification answers left blank.** The request proceeds on assumptions and
   never asks a second round. *(Task 9: `test_blank_answers_do_not_loop`.)*
4. **The user picks an alternative after a new data release was loaded.**
   `/v1/permits` uses the release stored with the original request.
   *(Task 9: `test_permits_uses_original_release`.)*
5. **Nothing in scope matches** (empty candidate list). The user gets a calm
   "tidak yakin" result and the API does not crash. *(Task 7: `test_empty_candidates_returns_unsure`.)*

### Task 8: Rules engine

**Files:**
- Create: `api/app/rules/engine.py`
- Test: `api/tests/rules/test_engine.py`

**Interfaces:**
- Consumes: the fixture data (Task 2) and the shared types (Task 6).
- Produces:
  - `risk_for(conn, release_id: int, code: str, attrs: Attributes) -> str | None`
  - `lookup_permits(conn, release_id: int, primaries: list[tuple[str, Attributes]], today: date) -> tuple[list[PermitItem], bool]`
    returns `(permits, stale_warning)`
- Matching rules (these are decided here, not left open):
  - A rule applies when, for every key in `conditions`, the attribute equals the
    required value **or** is `None`.
  - When the match relied on a `None` attribute, the item gets a
    `condition_note`: `Berlaku jika <label>`. Labels come from
    `ATTR_LABELS = {"packaged": "produk dijual dalam kemasan", "served_on_site": "makanan disantap di tempat", "has_seating": "ada tempat makan", "sells_online": "dijual online", "animal_products": "memakai bahan hewani"}`;
    for a `False` requirement the label is prefixed with `tidak `.
  - Only rows with `valid_to IS NULL OR valid_to > today` are used.
  - Merging: one item per `permit_id`, with `for_kbli` holding every code that
    requires it, sorted. The order is the minimum `step_order` across those
    codes, then the permit name. The result is renumbered from 1.
  - `risk_for` returns the highest applicable `risk_level`, in the order
    rendah < menengah_rendah < menengah_tinggi < tinggi.
  - `stale_warning` is true if any returned item has
    `last_verified < today - 183 days`.

**Interfaces:**
- Consumes: everything from Tasks 2 and 5–8.
- Produces:
  - **Endpoints:**
    - `POST /v1/analyze`: `AnalyzeRequest{description: str, answers: dict[str,str] | None}`
      → `AnalyzeResponse`, a union on `status`:
      `needs_clarification{request_id, questions}`, `out_of_scope{request_id, message}`
      or `ok{request_id, result}`. The `result` shape matches design §6.4.
    - `POST /v1/permits`: `{request_id: UUID, primary_codes: list[str]}` →
      `{permits, stale_warning}`
    - `POST /v1/feedback`: `{request_id, helpful: bool, comment: str | None}` →
      `204`
  - **Config:** `Settings` with `database_url`, `llm_mode: Literal["real","fake"] = "real"`
    and `embedder: Literal["bge","fake"] = "bge"`. App dependencies build
    `LlmClient` or `FakeLlm.canned()`, and `BgeM3Embedder` or `FakeEmbedder`,
    from these.
- Pipeline in `analyze()`, following design §6.3:
  1. `redact` the description and the answers.
  2. `understand`.
  3. Branch: out of scope → `out_of_scope` with the message
     `Maaf, jenis usaha ini belum didukung. Saat ini kami baru membantu usaha kuliner mikro dan kecil.`;
     questions → `needs_clarification`.
  4. Map 2020 codes, then `search_kbli` for each activity using the activity
     label plus the redacted description as the query.
  5. `select_codes`. If unsure → `ok` with an empty `activities` list and the
     scope note `Kami belum yakin kode KBLI yang tepat. Coba ceritakan lebih rinci apa yang kamu jual dan bagaimana menjualnya.`
  6. `risk_for` for every pick; `lookup_permits` for the primaries.
  7. Build `assumptions`: add `Dianggap usaha mikro/kecil` when size is not
     `menengah_besar`.
  8. Write `query_log` in every branch, with the redacted input, the
     `Understanding` JSON, the output JSON, the release id, the model, summed
     tokens and cost, and the latency.

  Each POST to `/v1/analyze` creates its own log row. The clarification round is
  a new row whose `clarifications` holds the answers.
